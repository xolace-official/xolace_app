# Design: Follow-Up Delivery via WhatsApp — meeting the user where they are

Generated by /office-hours on 2026-07-18
Branch: chore/channels-research
Repo: xolace-official/xolace_app
Status: APPROVED
Mode: Startup

## Problem Statement

Xolace's follow-up system today has exactly two delivery paths for a check-in: an APNs
push notification (fired by a durable Convex workflow after a tier-based sleep — 45min
acute / 12h elevated / 24h standard, verified in `convex/followUps.ts` and
`convex/lib/followUpCadence.ts`) or an in-app card (surfaced on reopen via `markReturn` if
the user opens the app before the push fires). Both paths require the user to be inside,
or actively return to, the Xolace app. The question: for the highest-stakes follow-up
moments (post-heavy-session, post-gave-up), does routing delivery through a channel the
user already lives in — starting with WhatsApp — reach people the current two paths miss?

## Demand Evidence

Qualitative only. No PostHog data exists on follow-up push delivered/opened/tapped rates
specifically (verified: no `posthog.capture` calls in `convex/notifications.ts` or
`convex/followUps.ts`; the `notifications` table tracks a `delivered` boolean but nothing
past that — open/tap is unmeasured). No one has sat behind a real user and watched them hit
this specific moment. The founder's confidence is grounded in general usage sense, not a
number or a documented incident. Industry data (searched, not Xolace-specific) supports the
direction: WhatsApp marketing/re-engagement open rates run 85-98% vs. 20-40% for push,
consistent with `docs/feat-analysis.md`'s cited 4x figure. This is real supporting evidence
for the *channel*, but it is not evidence that Xolace's specific follow-up push is
currently underperforming — that gap is unmeasured.

## Status Quo

Push notification (APNs) + in-app card, both scoped to the user opening the Xolace app.
`sendFollowUpNudge` gates only on `preferences.notifications.enabled` (no per-type toggle,
no quiet-window, by deliberate early-stage design per code comments) and sends the same
`cardText` the in-app card would show, with a fixed recency-anchored body substituted for
acute tier. If the user doesn't open the app and doesn't act on the push, the card silently
expires at `expiryMs` (48h/7d/14d by tier) via `markCardExpired` — no second channel, no
escalation beyond the two in-app pushes already scheduled at stage1/stage2.

## Target User & Narrowest Wedge

Target: a Xolace user with a pending follow-up card (any tier) who has WhatsApp installed
and has opted in to receiving check-ins there — most consequential for acute/elevated tier,
where a missed check-in is highest-stakes, but not restricted to those tiers.

Narrowest wedge, per the founder's own choice (overriding the recommended
instrument-first canary — see Premises): add the WhatsApp Cloud API component
(`convex-whatsapp` per `docs/feat-analysis.md`, not yet installed or spiked — Effort below
excludes component bring-up/Meta app review/number provisioning time, which is a real
unknown) as an **opt-in, outbound-only delivery leg**
on the existing `sendFollowUpNudge` path. Same trigger (`stage1Ms`/`stage2Ms` sleep fires
unchanged), same cadence, same `cardText` content already computed — only the delivery
mechanism branches: if the user has an active Xolace+ entitlement (WhatsApp delivery is a
real per-message cost, unlike free APNs push — see Constraints) and has opted in and
verified a WhatsApp number, send via WhatsApp template message **instead of** the APNs push (replace, not alongside — sending
both would defeat the WhatsApp-vs-push comparison in Success Criteria and double-notify the
user); if the WhatsApp send fails for any reason (invalid number, template rejected at send
time, user blocked the business number, or templates not yet Meta-approved), fall back to
the existing APNs push in the same nudge call — the highest-stakes tiers (acute/elevated)
must never silently drop a check-in because a WhatsApp send failed. No inbound webhook, no
two-way reply, no auto-fire mode change. This is deliberately the same "confirm-mode first,
no autonomous new surface area" shape as the sibling Trusted Contact Notify design's
Approach A — but WhatsApp, not SMS, per the founder's explicit call that these are
independent channel decisions (see Premises #2).

## Constraints

- WhatsApp Business requires pre-approved message templates for business-initiated
  (non-24h-window) messages — the follow-up nudge is exactly this case (arbitrary elapsed
  time since the user's last app interaction). Template copy must go through Meta's approval
  process before this can ship; treat as a lead-time dependency, not pure engineering effort
  (mirrors the A2P 10DLC point already flagged in the Trusted Contact Notify doc for SMS).
- Xolace's non-clinical voice constraint applies to WhatsApp template copy exactly as it
  does to the existing push body: no diagnosis language, no "you're in crisis" framing —
  the acute-tier body already in code ("Just checking in on what you worked through a
  little while ago. We're here.") is a reasonable template starting point.
- WhatsApp number is new PII (distinct from the user's Xolace account) — needs the same
  privacy-first handling as the rest of the schema: accessible for deletion, purged by
  `accountDeletion.ts` (which enumerates tables explicitly — a new WhatsApp-opt-in table or
  field must be added there or it outlives account deletion; flagged from a prior learning).
- Must not silently change `sendFollowUpNudge`'s existing gating (`notifications.enabled`
  only) — WhatsApp opt-in is an additive precondition on the delivery leg, not a new gate on
  whether a follow-up fires at all.
- The premium entitlement check (`hasPremium`) gating the WhatsApp branch must fail closed
  to APNs push on any error (e.g. a transient RevenueCat component hiccup) — wrapped in
  try/catch alongside the existing WhatsApp-send failure handling, so an entitlement-check
  error never breaks the whole nudge, only the WhatsApp leg. (CEO review Finding 2A)
- **WhatsApp delivery is a real per-message cost (unlike APNs push, which is free) — gated
  behind Xolace+.** Founder call, mid-review: free-tier users keep push + in-app card only;
  WhatsApp delivery requires an active Xolace+ entitlement, checked via the existing
  `usePlusEntitlement` pattern (server-side equivalent, not client-only) alongside the
  opt-in + verified-number precondition. This changes Approach A's gating from
  "notifications.enabled only" to "notifications.enabled AND isPlus" for the WhatsApp leg
  specifically (push/in-app remain ungated, per existing behavior).
- Meta requires a way for the recipient to stop business-initiated WhatsApp messages
  (opt-out/unsubscribe) — must be built alongside opt-in, not deferred. Given this design is
  explicitly outbound-only (no inbound webhook), the opt-out control lives **in-app only**
  (a Settings toggle disables WhatsApp delivery and reverts to APNs push) — the recipient
  cannot opt out via a WhatsApp reply in v1, since there is no inbound listener to receive
  one. `/plan-eng-review` must confirm an in-app-only opt-out satisfies Meta's business
  messaging policy before this ships; if it doesn't, a minimal inbound STOP-keyword listener
  (narrower than full two-way reply, but still new inbound surface area) becomes required
  scope, not optional.
- Until WhatsApp templates are Meta-approved, opted-in users must still receive their
  check-in via the APNs fallback above — opt-in UI should not ship expecting templates to be
  ready on day one; the fallback path is what makes shipping opt-in ahead of template
  approval safe.
- Meta imposes WhatsApp Business messaging tiers (1K/10K/100K unique recipients/24h,
  escalating only with account quality history) — `/plan-eng-review` must confirm expected
  opted-in volume stays under the starting tier before launch. (CEO review Finding 1A)
- Requires a global WhatsApp-delivery kill switch (a single preference/env flag forcing all
  follow-up delivery back to APNs push regardless of per-user opt-in) — cheap insurance
  against a full Meta suspension of the WhatsApp Business number, distinct from the
  per-send fallback-on-failure already specified above. (CEO review Finding 1B)

## Premises

1. The problem is real but unconfirmed: no PostHog data exists on follow_up push
   delivery/open/tap rates, and no one has observed a real user miss a follow-up
   specifically. The wedge is justified by founder intuition + industry stats, not Xolace's
   own numbers. — AGREED (explicitly accepted as a known gap, not resolved before building)
2. WhatsApp (this feature) and Twilio SMS (Trusted Contact Notify, already approved) are
   independent channel decisions, not gated by each other. The founder explicitly rejected
   treating the sibling doc's SMS choice as binding here — willing to run two messaging
   vendor integrations in parallel because the two features serve different relationships
   (Xolace-to-self vs. Xolace-to-third-party). — AGREED (revised from initial draft, which
   proposed treating them as coupled)
3. Future-fit is explicitly uncertain per the founder's own answer — this wedge is justified
   by one use case (follow-ups) today, not committed platform infrastructure for the
   Phase 2 proactive-support vision. If the other `feat-analysis.md` WhatsApp ideas (weekly
   summary, two-way re-entry) never ship, this is a single-purpose channel add for one
   notification type, not a platform bet. — AGREED

## Cross-Model Perspective

Second opinion (Codex) was offered and declined for this session — skipped, proceed on
founder judgment + landscape search alone.

**Landscape search finding:** WhatsApp business-messaging open rates (85-98%) meaningfully
outperform push (20-40%) in general re-engagement contexts, and mental-health-app-specific
sources note WhatsApp performs especially well for high-value touchpoints (weekly summaries,
milestones). This directionally supports the wedge. A separate finding is a caution, not a
contradiction: re-engagement literature warns against single-channel strategies and stresses
behavioral triggers over calendar-based sends — Xolace's existing tier-based cadence is
already behavioral (keyed to session outcome, not a calendar), so this caution is already
satisfied by the current design; it does not argue against adding WhatsApp as a second leg.

## Approaches Considered

### Approach A: Minimal viable — WhatsApp outbound-only on the existing push moment (RECOMMENDED by reviewer, CHOSEN by founder)
Effort: S/M, excludes `convex-whatsapp` component bring-up (see Narrowest Wedge — real
unknown, not yet spiked). Add `convex-whatsapp` component. Extend `sendFollowUpNudge` to
branch on a new WhatsApp opt-in + verified-number precondition; send via WhatsApp template
when present, falling back to APNs push on any WhatsApp send failure (replace, not
alongside — see Narrowest Wedge). New settings UI to capture and verify a WhatsApp number,
plus an in-app opt-out toggle (see Constraints — Meta opt-out requirement).
Pros: Ships fast, reuses 100% of the existing cadence/tiering/content-generation machinery,
zero change to trigger logic or workflow internals, tests real channel-preference demand
directly.
Cons: WhatsApp template approval has its own lead time outside engineering control. Adds a
second PII field needing the same deletion-pipeline wiring as `trustedContacts`. Ships ahead
of any confirmation that the underlying problem (push isn't landing) is real for Xolace
specifically.

### Approach B: Full vision — WhatsApp two-way, reply reopens a session
Effort: L. Everything in A, plus an inbound webhook so a WhatsApp reply ("I'm back" /
"feeling heavy") triggers `sessions.initiate` directly with a deep link, matching
`feat-analysis.md`'s full "two-way session initiation" pitch.
Pros: Matches the complete zero-friction re-entry vision described in feat-analysis.md.
Cons: Real new surface area — inbound webhook signature verification, keyword parsing,
session-open-from-an-unauthenticated-external-message, and a race between the WhatsApp
reply and an in-app open — built before Approach A has validated whether WhatsApp delivery
even changes follow-up engagement for Xolace's users at all. Sequencing risk backwards, same
shape as the sibling doc's Approach A-vs-B reasoning for Trusted Contact Notify.

### Approach C: Narrower than both — instrument first, no new vendor yet
Effort: XS. Before adding WhatsApp, close the measurement gap: add PostHog capture (already
installed) for follow_up push delivered/opened/tapped, run for 1-2 weeks, get a real number
before committing to a vendor integration.
Pros: Turns "qualitative signal, no numbers pulled" into an actual answer. Cheapest,
most reversible option — no vendor dependency, no new PII, no template-approval lead time.
Cons: Doesn't test the channel-preference question directly — a founder confident in the
direction may see this as delay rather than rigor.

## Runtime Mechanism Correction (Outside Voice, Claude subagent — accepted)

`sendFollowUpNudge` is an `internalMutation`; Convex mutations cannot `fetch()`. The existing
push path already shows this constraint's shape: `notifications.schedule` calls the
`pushNotifications` Convex component (`@convex-dev/expo-push-notifications`) and writes
`notification_log.delivered: true` *before* the send call executes — the write is optimistic,
not a confirmed result, because a mutation cannot wait on a real network round-trip.
The design's "if WhatsApp send fails, fall back to push in the same nudge call" assumed
synchronous failure detection that this runtime doesn't support as originally described.

**Correction:** the WhatsApp-branch dispatch must be an `internalAction` (which can
`fetch()`/call components and observe real synchronous success/failure from the WhatsApp
Cloud API's accept/reject response), not inlined in the `internalMutation`. This enables a
true try-WhatsApp-then-fallback-to-push flow within one logical call — `sendFollowUpNudge`
schedules or delegates to this action rather than performing the WhatsApp send directly.
`/plan-eng-review` owns the exact split (e.g. `sendFollowUpNudge` remains the mutation entry
point but hands the channel-selection + dispatch to a new internalAction that itself falls
back to `notifications.schedule` on WhatsApp failure).

## Observability Requirement (CEO review Finding 8A)

Success Criteria's WhatsApp-vs-push resolution-rate comparison is unmeasurable without
tracking which channel a given `follow_up_cards` row was actually delivered through
(post-fallback-resolution — i.e. "whatsapp" only if the WhatsApp send actually succeeded,
"push" if it fell back for any reason). Required, not optional: add a `deliveryChannel`
field to `follow_up_cards` (or equivalent) set at send time, plus a PostHog capture event
mirroring it. This is what makes the Success Criteria section answerable at all, not a
nice-to-have.

## Testability Requirement (CEO review Finding 6A)

The channel-selection decision (WhatsApp vs. push, given entitlement + opt-in + verified +
kill-switch state) must be extracted into a pure, Convex-free function — following the same
pattern `convex/lib/followUpCadence.ts` already establishes for cadence/tiering logic
(deliberately kept import-free specifically so it's `bun:test`-unit-testable without mocking
Convex `ctx`). `/plan-eng-review` should place this alongside `followUpCadence.ts` or as a
sibling `lib` module, not inlined in `sendFollowUpNudge`.

## Recommended Approach

Reviewer's recommendation was **Approach C** (instrument before committing to a vendor,
since premise #1's unconfirmed-demand gap is the actual blocker). The founder explicitly
chose **Approach A** instead, overriding that recommendation — noted as a founder signal:
willing to commit engineering effort to a wedge on qualitative conviction rather than wait
for a metrics gate, and willing to accept a second parallel messaging vendor integration
rather than consolidate on the sibling design's SMS choice. Approach A is the design carried
forward into `/plan-eng-review`.

## Success Criteria

- WhatsApp opt-in rate among users with a pending or resolved follow-up card — first-order
  adoption signal.
- Follow-up card resolution rate (any response, not just "processed") for WhatsApp-delivered
  vs. push-delivered cohorts — the actual channel-preference test this wedge exists to run.
- WhatsApp opt-in as a Plus-conversion signal — does gating this behind Xolace+ move any
  free-tier users to upgrade, given it's the entitlement check gating the leg?
- Zero WhatsApp template rejections/bans from Meta due to clinical-framing violations — the
  qualitative guardrail Xolace's voice constraint is meant to protect.

- WhatsApp Cloud API component (`convex-whatsapp`) not yet installed — scoped in
  `docs/feat-analysis.md` but not built.
- Meta WhatsApp Business template approval — external lead time, should start early,
  independent of code readiness (same shape as the Twilio A2P 10DLC dependency already

- Related but explicitly independent: Trusted Contact Notify (APPROVED design,
  `nathan-chore-channels-research-design-20260718-082326.md`, same branch) chose Twilio SMS
  as its channel. This design does not supersede or depend on that one — the founder

- Reuses `convex/followUps.ts` (`sendFollowUpNudge`) and `convex/lib/followUpCadence.ts`
  cadence/tiering — no schema change needed to the follow-up system itself, only a new
  WhatsApp opt-in/number field (table or field TBD in `/plan-eng-review`).
- Reuses `convex/lib/premium.ts`'s `hasPremium(ctx, profile)` server-side seam for the Plus
  gate — no new entitlement-check code needed, confirmed present in the codebase.
- **Forward-compat note (not current scope):** a possible future ElevenLabs WhatsApp voice/
  text agent integration (raised post-review, not designed) cannot share a phone number with
  this feature — WhatsApp only allows one active tech-provider/BSP per number, and ElevenLabs'
  own docs confirm this exclusivity (Meta's Multi-Solution Conversations isn't GA). No action
  needed now: a WABA supports multiple phone numbers, so ElevenLabs would simply get its own
  number whenever it becomes real. Provision the follow-up number as its own number, not with
  an assumption it's the only one — that's the only thing to get right at setup time.
