## Problem Statement

The Listener Suggestion pilot (APPROVED design, `nathan-chore-channels-research-design-
20260718-165134.md`) planned to connect a user to one of 6 trained ambassadors via
direct-reveal: showing the user the ambassador's real WhatsApp/phone number and letting them
text off-platform. On team review, this was flagged as too much risk for too little cost
saved — conversations happening entirely outside Xolace mean zero visibility, zero
moderation, and zero audit trail if something goes wrong, which matters more than usual given
the app's mental-health context. The team decided to build a minimal in-app chat instead —
even v1 should be architected as the foundation for the eventual social layer (peer-to-peer
chat), not a one-off hack for 6 ambassadors.

## Demand Evidence

Unchanged from the superseded design — the underlying human-connection bet (a real listener,
not just AI mirror or anonymous peer content) was already validated there. What's new in this
session is not new demand evidence; it's a risk/cost re-evaluation of the *contact mechanism*
for that already-validated bet.

## Status Quo

Today: the Listener Suggestion pilot is coded against Approach A's direct-reveal contact
model but has not shipped to real users (the `listenerSuggestionsEnabled` kill-switch defaults
to `false` pending the ambassador-consent conversation, per the superseded design's Deploy-
Order Requirement). No in-app chat exists anywhere in the app today — this is greenfield.

## Target User & Narrowest Wedge

Same target user as the superseded design (a user who just finished a moderate-to-high
intensity session). Narrowest wedge, revised: **text-only, 1:1, ambassador-initiated-eligible
conversation inside the app**, built on Stream Chat, replacing the wa.me deep link with an
in-app chat screen. No group chat, no media/voice, no read receipts beyond what Stream gives
for free, no browse/directory UI (unchanged from the superseded design).

## Constraints

Carried forward unchanged from the superseded design (see that doc's Constraints section for
full detail — escalation-exclusion, non-clinical copy, session-ownership auth pattern, etc.).
New constraints from this session:

- **Ambassadors become real addressable entities, not a hand-seeded info roster.** In-app
  chat requires both sides of a conversation to be identifiable participants — the "6 rows,
  no admin UI" model from the superseded design's Approach A no longer fits. Ambassadors need
  a lightweight account-like identity (tied into or alongside the existing `users` model) and
  a public-safe profile surface (name, bio, whatever is appropriate to show a user before/
  during a conversation) — this is a genuine, not cosmetic, architecture change from the
  original pilot scope, exactly as the founder flagged mid-session.
- **Stream Chat becomes a new data processor for conversation content.** Content exchanged
  between a user and an ambassador is mental-health-adjacent. Stream's DPA, data-residency,
  and subprocessor terms need review before real user data flows through it — same posture
  the app already applies to other PII via `consent_records`. This does not block writing
  code; it blocks flipping the feature live, mirroring the ambassador-consent gate already in
  the superseded design.
- **Team capacity is the deciding constraint, not feature completeness.** The team does not
  have engineering headcount to spend building and maintaining custom chat infrastructure
  (presence, read receipts, moderation, search, offline sync) if/when this grows into the real
  social layer. This is why Stream was chosen over custom despite custom being cheaper and
  more private today — see Premises below.
- **Data retention/deletion for Stream-hosted content is a real architecture gap, not just a
  DPA paperwork item.** Xolace's existing data-lifecycle machinery (`convex/jobs/
  dataRetention.ts`, `dataWipe.ts`, the crisis-exclusion posture in the Cognition Layer
  Constitution) is entirely Convex-native — it has no reach into content stored on Stream's
  servers. Before the DPA/data-residency review is treated as sufficient, this design needs an
  explicit answer for: what happens to a Stream conversation's message history when a user
  deletes their account or invokes their data-deletion right, and whether Stream's own
  retention/deletion API is wired into the same jobs that already purge Convex tables. This is
  a hard prerequisite for `/plan-eng-review`, not a follow-up detail.
- **Mid-conversation escalation is not addressed.** The superseded design's escalation
  exclusion only gates whether a *suggestion* is shown (existence check on `escalation_events`
  at session end). It says nothing about a session where `escalationTriggered` fires *while* a
  user is already mid-conversation with an ambassador via Stream. This design needs an
  explicit answer — even if the answer is "out of scope for v1, ambassadors are told during
  onboarding to escalate to Xolace's existing crisis-resource path themselves if a
  conversation turns that direction" — rather than silence.

## Approaches Considered

### Approach A: Custom Convex-native chat
Two new tables (`conversations`, `messages`) + Convex's reactive `useQuery` for real-time,
zero new vendor, full audit trail stays in the existing DB, reuses `requireAuth`/
`requireSessionOwnership`, `convex/ai/safeguard.ts` moderation pipeline, and `notification_log`
push infra. Cheapest and most private option today.
Pros: $0 marginal cost, no new data-processor relationship, no token-minting integration
point, everything queryable via the same `mcp__convex` tooling already in daily use.
Cons: no prebuilt UI kit (small cost at 1:1/text-only scale, real cost if the social layer
later needs group chat, presence, typing indicators, read receipts, or search) — that
engineering time has to come from the same small team, later, under more time pressure.

### Approach B: Stream Chat (RECOMMENDED, chosen)
Verified via Stream's pricing page and RN/Expo SDK docs: free tier covers 1,000 MAU / 100
concurrent connections — comfortably covers 6 ambassadors + a few hundred users — and core
moderation (dashboard, message flagging, profanity filter/blocklist, mute/ban/block, moderator
roles, pre-send hooks) ships on the free tier, not gated behind the paid "Start" tier as
initially assumed (corrected mid-session) — only AI-powered auto-moderation is a paid/
enterprise upsell. RN/Expo SDK is mature with prebuilt UI (message list, push, offline sync).
Requires a server-side token-minting step (JWT signed with Stream's API secret) alongside
existing Clerk auth — a new integration surface, not a Clerk replacement. No dedicated Convex
component exists for Stream (checked convex.dev/components); if a wrapper is built, it should
be a plain integration module (e.g. `convex/integrations/stream.ts`), not a formal published
Convex component — there's exactly one internal consumer, so packaging it as a component is
unwarranted ceremony.
Pros: ships fastest, moderation tooling included free, strongest foundation if/when the social
layer expands to real peer-to-peer chat, doesn't consume scarce engineering time on chat
infrastructure the team isn't sized to build and maintain.
Cons: new data-processor relationship for mental-health-adjacent conversation content (DPA/
data-residency review required pre-launch), migrating off Stream later is the harder direction
(export out of a proprietary format, prebuilt UI gets rebuilt) — accepted as "hard but not
impossible," which the team judged sufficient given the capacity constraint.

### Approach C: Hybrid — custom now, Stream later at social-layer scale
Ship the minimal custom Convex chat for the 6-ambassador pilot now; treat Stream as the future
option once the social layer actually needs group chat, presence, or search, deciding again
then with real usage data.
Pros: defers the vendor/DPA question until it's actually load-bearing, cheapest and most
private for the pilot specifically.
Cons: explicitly rejected — the team's stated intent is to build the chat layer once, knowing
it needs to become the social-layer foundation, precisely because they don't have spare
engineering capacity to build it twice (once custom now, once on Stream or elsewhere later).

## Recommended Approach

**Approach B (Stream Chat).** Chosen on team-capacity grounds, not cost or moderation-quality
grounds (those turned out to be close to a wash once verified) — a small team building a
mental-health app shouldn't sink scarce engineering hours into chat infrastructure (presence,
search, offline sync, moderation tooling) when a $0-at-this-scale vendor already provides it,
and the team explicitly accepted that migrating off Stream later, if ever needed, is an
acceptable "hard but not impossible" cost against that tradeoff.

## Engineering Review (via /plan-eng-review, 2026-07-24)

Locked architecture decisions, resolving this doc's Open Questions:

1. **Ambassador/listener model:** thin `isListener: boolean` flag on the existing `users`
   table (eligibility) + a new, separate `listenerProfiles` table (userId, displayName, bio,
   photoUrl, `complete: boolean`, `active: boolean`) for the public-facing data. Ambassadors
   are already real Xolace users (not a hand-seeded roster, per the founder's correction
   mid-review) — this keeps the core `users` schema/type clean while isolating
   listener-specific fields, indexing (`by_complete_and_active` for the directory), and
   lifecycle in their own table, matching this repo's existing Convex convention of child
   tables with a foreign key back to the parent.
2. **Scope reversal, deliberate:** the directory/browse UI explicitly excluded by the original
   `/office-hours` session (Q4) is back in scope. Two entry points now: (a) post-session
   suggestion (unchanged), (b) a directory listing all listeners with `complete: true &&
   active: true` profiles. A listener's profile is not listed until they finish filling it in.
3. **Stream token minting:** direct `fetch` calls signing JWTs with Web Crypto, staying in
   Convex's default runtime — no Stream server SDK, no `"use node"` split.
4. **Data retention:** account deletion (`convex/jobs/accountDeletion.ts`) calls Stream's
   delete-user API inline, in the same job as the rest of the deletion flow. If the Stream
   call fails, the rest of deletion proceeds (matches the app's existing fail-open-but-log
   posture) and the failure is logged for retry, rather than blocking a user's deletion
   request on a third-party outage.
5. **Mid-conversation escalation:** no automated detection in v1 — ambassadors are trained to
   recognize concerning conversations and redirect to Xolace's existing crisis-resource path
   themselves. Automated detection (piping Stream messages through the safeguard classifier)
   is deferred to `TODOS.md`.

**Critical gap resolved:** Stream delete-user failure during account deletion now has an
explicit answer (proceed + log + retry) instead of silence — see Decision 4 above.

### Cross-Model Tension (Outside Voice, Claude subagent — Codex errored, model unsupported)

1. **Ambassador consent scope, resolved:** the outside voice flagged that consent just got
   heavier (public-profile account inside a mental-health app, mediated by a vendor — not just
   "share your WhatsApp"). Confirmed: this is already being run as a full standalone
   re-consent, not an edit to the original ask. Any ambassador who declines public visibility
   is simply not eligible to become a listener — no partial/soft version.
2. **Request/accept flow, new — added provisionally.** A chat does not open instantly on
   suggestion or directory-tap. A user's contact intent creates a request; the listener must
   accept before the Stream channel becomes active. This came from one ambassador's stated
   preference during the (in-progress) consent conversation — **pending confirmation from the
   remaining 5.** This resolves most of the outside voice's concern about rotation/cooldown
   interacting badly with an already-open conversation: an inactive or capped listener simply
   stops receiving new requests, rather than needing logic to interrupt a live chat. Schema
   implication: `listenerChatRequests` (or a status field on the channel-provisioning record)
   needs a `pending | accepted | declined` state, not just "channel exists." **If any of the
   remaining 5 ambassadors prefer instant-open instead, this needs to be revisited as a
   per-listener setting, not assumed universal.**
3. **DPA fallback, resolved:** if Stream's DPA/data-residency terms turn out unacceptable for
   mental-health content, the explicit fallback is Approach A (custom Convex chat) — already
   fully specced in this doc's Approaches Considered section. This isn't a redesign from
   scratch if Stream is rejected; it's falling back to a rejected-but-viable option, not
   starting over. No new kill-criterion mechanism needed beyond what already exists (the
   `listenerSuggestionsEnabled`-style kill-switch pattern gates it live regardless of backend).

Two other outside-voice points were surfaced but not re-opened as decisions: the directory
scope reversal (already explicitly confirmed with the user, not silently waved through) and
whether Stream is justified by a speculative future social layer (already the team's explicit,
reasoned tradeoff on capacity grounds — see Premise #3 — not new information).

### Worktree Parallelization
Two largely independent lanes once schema is locked:
- **Lane A (backend):** `convex/schema.ts` (`listenerProfiles`, `isListener` flag),
  `convex/listenerChat.ts` (eligibility, rotation, directory query), `convex/integrations/
  stream.ts` (token minting, channel provisioning, delete-user wiring).
- **Lane B (UI):** chat screen, directory screen, profile-completion screen, session-end
  suggestion card update — all under `src/features/listener-chat/`.
Lane B depends on Lane A's Convex function signatures existing (even as stubs) before wiring
real data, so launch A first or agree on function signatures upfront, then run both in
parallel worktrees.

### Performance
No concerns at this scale (single-digit ambassadors, low message volume, 1:1 conversations
only). The eligibility/rotation query is index-bounded (per this repo's Convex conventions);
no N+1 patterns introduced.
