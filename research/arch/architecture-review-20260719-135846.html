Architecture Deepening Review · 2026-07-19

Xolace — turning shallow modules deep

Explored the branch hot spots (reflect/, purchases/, and the convex/ AI + jobs pipeline). One theme runs through every finding:

Domain invariants are re-stated at call sites instead of being owned by one module.

The team already knows the deepening move — lib/aggregates.ts and episodicMemory.purge* are exactly it: one owner of a rule, many callers. It just hasn't been applied to the AI pipeline, the delete/eligibility seams, or the client-side session echo. Two findings below aren't friction — they're latent correctness/privacy bugs hiding as friction.

Strong

2 · A single content-eligibility predicate

Strong

⚠ Safety invariant (crisis excluded from the peer pool) re-derived in three places.

Files: jobs/reflectionAnonymizer.ts:43-52, jobs/reflectionDistiller.ts:32, ai/episodicMemory.ts:99

Problem

"May this session's text leave the user's private space?" is the single most safety-critical predicate in the product (your memory note: crisis sessions must never be distilled or contributed to the peer pool). It is currently answered in three different modules with three different field sets: the anonymizer checks kept !== true && contributedReflection !== true && safeguardLevel === "crisis"; the distiller checks only kept !== true; episodic ingest checks only safeguardLevel === "crisis". Nobody owns "is this session poolable." A future flag (say a redacted field) has to be remembered in all three — the identical failure mode as Candidate 1, but the blast radius is a privacy leak.

episodicMemory
crisis

Three answers to one safety question. Add a gate → update 3 → miss one → text escapes.

After — one predicate

anonymizerdistillerepisodicMemory
↓ all ask ↓ sessionContentEligibility(session)
→ { poolable, distillable, ingestable }

The safety invariant lives in one pure function — the interface is the test surface.

Benefits

  • A pure predicate is trivially unit-testable — a table of (kept, contributed, safeguardLevel) → expected verdict. This is the one place in the codebase most deserving of a test, and it currently has none.
  • The two thin queries (getSessionKept, loadSessionForAnonymize) that exist only to feed these ad-hoc checks collapse into the predicate's loader or inline into their callers.

3 · Extract the decisions out of the generateMirror god-action

Strong

Files: convex/ai/process.ts:41-460 (one ~420-line "use node" action) + the ~15 modules it orchestrates

Problem

"What happens when a session is processed" is one 420-line node action that interleaves pure policy decisions with I/O to 8 tables. The decisions — tone downgrade (:99), isEscalation (:247), requiresFollowUp (:253), riskFlag mapping (:331), exercise fallback (:361) — are only reachable by mocking the entire Anthropic + RAG + DB world. There's no seam, so none of them are tested. The instinct to "split the action into smaller actions" is the wrong deepening: more actions = more runQuery round-trips and worse locality. The right move is to pull the pure decision core out, leaving a thin I/O driver.

Benefits

  • The seam moves to where the bugs are. decideMirrorOutcome is a pure function — every routing rule gets a unit test without touching Anthropic or Convex.

4 · Derive the reflect screen from session.state

Strong

Files: use-reflection-machine.ts, reflection-reducer.ts, session-service.ts, use-session.ts (227 lines), use-path-session.ts

Problem

The server already owns the session state machine. The client re-encodes "server state → which screen" three times: the reducer's server-echo actions, a guard-laden useEffect bridge (use-reflection-machine.ts:98-155, note the tell-tale if (state.screen !== 'processing') guards where two owners fight over one transition), and a pure mapServerStateToScreen (session-service.ts:45-68) built for exactly this — that is dead code, zero imports. Tapping "That's it" writes the same transition in four files. And because useSession is welded to the reducer, the path screens couldn't reuse it — forcing the near-duplicate usePathSession, so path-transition rules now live in three places (server throw + two client guards).

Before — 3 encodings echo one state

server: session.state ↓ echoed by ↓
reducer echo actions bridge useEffect + guards mapServerStateToScreen
↓ coupling forces ↓
useSession (227L) usePathSession (clone)

One tap → same transition written in 4 files.

After — server is truth, screen derived

server: session.state (source of truth) ↓ derived by ↓ screen = f(session.state)
(the ex-dead mapper, revived) ↓ reducer keeps only ↓ local-only screens
typing · nudge · clarify text · textures ↓ one hook, not welded ↓ useSessionActions (both screens select)

Deletes the echo half of the reducer, the guard effect, and the clone.

Benefits

  • Deletion test passes hard: the dead mapper is ~80% of the derivation already; reviving it lets you delete the server-echo actions, the guard-laden effect, and the reason usePathSession exists.
  • Kills a real bug class: today submitClarification branches on error.message.includes('Maximum refinement turns') — a server reword silently drops the user into the wrong branch. Deriving from typed state (the input_too_long ConvexError code at sessions.ts:235 is the model) makes the client branches testable and reword-proof.

Top recommendation — tackle first

Candidate 1: one owner for the cascade-delete graph.

It's the only candidate that is a live bug today, not just future friction — the retention sweep already leaves orphaned escalation_events and other child rows behind a deleted session. For a privacy-first mental-health product, silent data-lifecycle divergence is the highest-stakes finding here, and the fix is the smallest, best-bounded diff of the six: extract two purge helpers, route three callers through them, add one property test. It also establishes the exact pattern — one owner, many callers — that Candidates 2, 3, and 6 all reapply, so doing it first sets the template.

Natural sequence: 1 → 2 (same shape, same privacy domain, ship together) → 3 (biggest testability win) → 4 (biggest client cleanup) → 5, 6 (edge polish).
