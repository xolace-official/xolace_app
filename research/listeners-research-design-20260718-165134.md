# Design: Listener Suggestion — a real human, offered at the right moment

Generated by /office-hours on 2026-07-18
Branch: chore/channels-research
Repo: xolace-official/xolace_app
Status: APPROVED
Mode: Startup (intrapreneurship)

## Problem Statement

Xolace's core loop ends in one of three places after a session: a solo exercise, anonymous
peer reflections, or exit. None of these is a real, present human who can talk back. The
founder observed that some users likely have nobody in their life to talk to at all, and
received direct feedback — "talking to someone real on this platform would actually help I
guess" — that a real person, not just the AI mirror or anonymous peer content, would help.
Xolace is training 6 ambassadors as peer counselors (7cups-style "listeners," name TBD) and
wants to introduce them now, in minimal form, rather than wait for the full social layer /
in-app chat to exist. The question: what is the smallest, safest version of "offer someone a
real listener" that ships before any in-app messaging infrastructure exists?

## Demand Evidence

One or two concrete quotes exist (per founder, including the one referenced above), not yet
a counted pattern across users — the founder was explicit about this being thin, not
fabricated. This is the same evidentiary shape as the sibling Trusted Contact Notify design
on this branch ("quotes exist... not yet pulled into this doc"). `research/
xolace-user-research-synthesis.md` independently shows strong adjacent demand: 6 of 7
ambassadors said yes to wanting peer reflections, and the same document surfaces a
"what now?" gap after clarity — users reaching emotional understanding with nowhere
satisfying to take it. A real listener is a plausible answer to that gap, but this specific
feature's own demand signal is qualitative and uncounted.

## Status Quo

Today, after a session, a user's only "human" options are anonymous peer reflections (see
`(protected)/peer-reflections` — resonance-based, not identity-based, no direct
conversation) or Trusted Bridge (an AI-drafted message the user actively composes and sends
to someone they already know — requires the user to have the presence of mind to use it).
Neither surfaces a new person the user doesn't already know, and neither is a real-time or
even asynchronous two-way conversation with someone trained to listen.

## Target User & Narrowest Wedge

Target: a Xolace user who just finished a moderate-to-high intensity session (heavy, but not
escalation-adjacent) and would value a real person to talk to, whether or not they have
someone in their own life (Trusted Bridge already covers "someone I know"; this feature
covers "someone new, trained to listen").

Narrowest wedge, per the founder's explicit choice: **post-session suggestion only** — no
browse/directory UI in v1. After a session meets an intensity threshold, and explicitly
excludes any session where an `escalation_events` record was triggered (that population stays
on Xolace's existing crisis-resource / human-review path — this feature does not touch it),
show a card: "Want to talk to someone?" with one of the 6 trained ambassadors' name, short
bio, and direct contact (WhatsApp/phone deep link). The user reaches out themselves — no
in-app chat, no masking, no matching algorithm beyond simple eligibility + rotation across
the 6. A user-facing disclaimer ("this is an early pilot, not professional counseling") and a
one-tap feedback link back to Xolace are required in the same surface, not follow-up polish.

## Constraints

- The v1 trust model is human vetting of a small, known cohort (6 ambassadors, physically
  close to the founder, in training, personally reviewable) — not platform infrastructure
  (no on-platform transcript, no flag/report system, no supervised review queue the way
  7cups' safety model works). This is an accepted tradeoff for a pilot at this scale, not a
  permanent design — it must be revisited before any listener outside this known cohort is
  added.
- **Ambassador consent is a pre-launch gate, not a soft follow-up.** Direct-reveal means each
  ambassador's real WhatsApp/phone number is shown to real users, on terms (timing,
  frequency, visibility into who's contacting them and why) they have not yet explicitly
  agreed to. This must be confirmed with all 6 ambassadors — including their preference on
  whether direct reveal is acceptable at all — before the feature is shown to any real user.
  Code can be built without waiting on this conversation; the feature cannot go live without it.
- Must not expand or reinterpret `escalation_events`' existing purpose (human review queue for
  safety) — this feature only reads **whether any `escalation_events` row exists for the
  session** (existence check, not a `triggerConfidence` threshold) to exclude it. A simple
  existence check is the correct gate here: any triggered escalation event, regardless of
  confidence score, means that session stays on Xolace's crisis-resource path, full stop.
- Xolace's non-clinical voice constraint applies to the suggestion card copy and the
  disclaimer — no diagnosis language, no "you're in crisis" framing.
- The ambassador roster (6 rows: name, bio, contact method/value) is new data about real
  people (not users) — treat with the same privacy-first handling as other PII (accessible
  for removal if an ambassador stops participating).
- The eligibility query must enforce the same session-ownership check used elsewhere in the
  codebase (`requireSessionOwnership` or equivalent) before returning any ambassador contact
  info — without it, a user could query another user's `sessionId` and see who was suggested
  to them (an IDOR risk on new PII-adjacent data).

## Premises

1. This is a third, independent track alongside Trusted Contact Notify (notify an existing
   caring contact) and WhatsApp Follow-Up Delivery (re-engagement channel), both already
   designed on this branch — not superseding or blocked by either. — AGREED
2. v1 trust model is human vetting of a small known cohort, not platform infrastructure —
   acceptable for a pilot with 6 ambassadors, must be revisited before opening to any
   listener outside this cohort. — AGREED
3. The suggestion fires on moderate-to-high intensity sessions, explicitly excluding any
   session with a triggered `escalation_events` record — that population stays on Xolace's
   existing crisis-resource path untouched. — AGREED
4. Contact exchange is direct reveal (ambassador's WhatsApp/phone shown to the user) for v1
   — **and ambassador consent to these specific terms is a pre-launch gate**, not a follow-up
   task. Revised after cross-model review flagged treating this as "pending discussion" as a
   sequencing risk, not a soft open question. — AGREED (revised)
5. This is the seed of the real social-layer listener feature, not throwaway. The durable
   piece is the matching/eligibility logic (who gets suggested a listener, when, with what
   audit trail); the contact-exchange mechanism is swappable — external channel now, in-app
   chat once the social layer ships. — AGREED
6. A user-facing disclaimer (early pilot, not professional counseling) and a feedback route
   back to Xolace are required v1 scope, not polish added later. — AGREED

## Cross-Model Perspective

Codex was attempted but errored (model not supported for this account/session) — fell back
to a Claude subagent per skill instructions, given only a structured summary of this session,
no visibility into the live conversation.

**Steelman:** "A trust-mediated warm handoff — Xolace's AI already knows a session is heavy;
instead of leaving the user alone with an exercise or a stranger's post, it offers a real
human from a small, personally-vetted cohort, with the matching logic built now so the 'who
talks to whom' decision engine survives the swap from phone numbers to in-app chat later."

**Key insight:** the founder's own framing — "durable piece = matching/eligibility logic;
contact mechanism = swappable" — correctly identifies this as a decision-system problem, not
a messaging-feature problem. The 48-hour build should spend its budget on eligibility and
audit logic, not on chat UI that gets thrown away later.

**Challenged premise (accepted, see Premise #4 above):** direct-reveal with no listener-side
consent gathered yet is a sequencing error, not a design nit — evidence that would prove it
wrong is a single ambassador saying "I'd rather this go through the app first" or "I want to
see who's contacting me before it happens." The fix costs one conversation with 6 people the
founder already trains regularly, which is cheaper than the code, so there's no reason not to
gather it before shipping to real users.

**48-hour prototype sketch (informed the approaches below):** reuse `sessions` +
`escalation_events` via a join, not new signal; new `listenerSuggestions` audit table
(sessionId, userId, ambassadorId, shown, respondedAt) as the durable eligibility/audit piece;
new hand-seeded `ambassadors` table (6 rows); one query gating on intensity + no escalation
event + round-robin/rate-limit across active ambassadors; one UI card at session-end with
disclaimer + feedback link; explicitly skip browse/directory, masking, listener dashboard,
and any admin CRUD for a 6-row roster.

## Approaches Considered

### Approach A: Minimal viable — direct reveal, hand-seeded roster (RECOMMENDED, chosen)
Effort: S/M (human ~2-3 days / CC ~30-40min, plus `@vllnt/convex-flags` install — see
`/plan-ceo-review` Section 1). Adopt `@vllnt/convex-flags` for both a global kill-switch
(disable the whole feature instantly, no redeploy) and per-ambassador active/inactive
override (replacing a plain `active` field) — sandboxed tables, "zero blast radius into
your schema" per the component's own docs, and its per-subject override mechanism doubles
as the ambassador self-pause toggle deferred in TODOS.md (D3.3), which this adoption
substantially de-risks even though it stays deferred as a UI/access question. **Dependency
risk noted and accepted:** the package is at v0.1.0-canary (single maintainer, 7 versions
published) — accepted given the small, easily-vendored surface of a boolean-flag use case;
if the package is abandoned, the flag-check call sites are trivial to replace. Pausing an
ambassador via the flag (rather than deleting their `ambassadors` row) preserves their
`lastSuggestedAt` history and audit trail for when they return. New
`ambassadors` table (name, bio, contactMethod, contactValue,
`lastSuggestedAt: optional number` — active state now lives in convex-flags, not a table
field — 6 hand-seeded rows, no admin UI). New `listenerSuggestions` table (sessionId, userId,
ambassadorId, `shown: boolean`) as the eligibility/audit trail, indexed `by_userId` for the
D3.4 cooldown check (per this repo's Convex conventions: always index instead of
`.filter()`) — **note this table can only
ever record that a suggestion was shown, never whether contact was actually made or
effective**, since the conversation itself happens over an external channel Xolace has no
visibility into; do not build or promise a "response rate" metric this data can't support.
One query joins `sessions` + `escalation_events` (existence check only, per Constraints
above) to gate eligibility (intensity threshold met, no escalation event exists, user has
completed at least one prior session — a first-session user should not see this, per the
2A/2B/2C fixes below) and picks the ambassador with the oldest (or null) `lastSuggestedAt`
among active ambassadors, then updates that field — least-recently-suggested selection, not
a separate round-robin cursor. **Feedback reuses the existing shake-to-open feedback tray
(`src/features/feedback-tray/`) rather than a bespoke form**: the suggestion card's "tell us"
link programmatically opens the tray with a new `productFeedback.submit` `kind: "listener"`
value (extending the current `"bug" | "idea"` union) and passes `sessionId`/`ambassadorId` in
the existing `context` object — this reuses 100% of the existing mutation, its rate-limiting,
inline error display, and preserved-input-on-failure behavior with zero new schema for
feedback itself. One UI surface: a card at session-end, gated by the query, showing name/bio
+ a `wa.me/<number>` deep link (plus the raw contact value shown as visible text, per 2B, in
case the user's phone has no WhatsApp) + mandatory disclaimer + the "tell us" link into the
existing feedback tray. If the eligibility query itself throws (escalation lookup fails,
convex-flags read fails), it fails CLOSED — caught, logged, suggestion suppressed, the rest
of session-end renders normally (per 2A). `ambassadors` and `listenerSuggestions` rows follow the same data-retention posture as
other operational (non-content) tables — no special anonymization pipeline, deleted if an
ambassador leaves the program or the pilot ends.
Pros: ships fast, matching/eligibility logic is the durable seed for the real social-layer
feature, matches the founder's stated wedge exactly, reuses existing signals with no new AI
call or classifier.
Cons: 6-row roster is edited by hand (fine at this scale, breaks down past ~15-20
ambassadors); ambassador phone numbers are exposed to users once shown (mitigated by the
consent-gate in Premise #4, not eliminated); the audit trail cannot confirm a conversation
actually happened, only that the door was opened.

### Approach B: App-mediated intro, no reveal
Effort: M (human ~4-5 days / CC ~1hr). Same eligibility/matching logic as A, but instead of
showing the user the ambassador's number, Xolace notifies the chosen ambassador (push or SMS)
that a user consented to be contacted, and the ambassador reaches out first.
Pros: ambassador's number never touches the app UI; every intro has a clean server-side
record; no direct-reveal consent gate needed since numbers are never shown to users.
Cons: real new build (an outbound notify leg to ambassadors, likely via the same messaging
component the sibling Trusted Contact doc is already adding); ambassador response latency
degrades the exact moment — right after a heavy session — where responsiveness matters most;
does not match the founder's explicit choice of direct reveal, made with full knowledge of
the tradeoff.

### Approach C: Static single-screen pilot, zero matching logic
Effort: XS (human ~half a day / CC ~15min). Skip eligibility/rotation logic entirely — one
static screen listing all 6 ambassadors with contact info, reachable from Settings or a
generic "need to talk to someone?" entry point, with no session-triggered suggestion at all.
Pros: cheapest possible way to test whether users want to reach a listener at all, before
building any matching logic.
Cons: discards Premise #5 (seed of the real thing) — no session-context signal, no audit
trail, doesn't test the actual product bet (a contextual suggestion at the moment it matters
most). The founder already rejected an equivalent narrower option when asked directly about
the wedge (Q4).

## Recommended Approach

**Approach A.** It is the smallest version that tests the real product bet — does a
contextual, post-session nudge toward a real trained listener change anything for a user —
while keeping the durable investment (eligibility/matching/audit logic) in the piece that
survives into the eventual social-layer chat feature. Approach B is real but premature: it
adds messaging infrastructure before Approach A has validated that users want the nudge at
all. Approach C is cheaper but throws away the one thing this pilot exists to learn.

## Open Questions

- **Exact intensity threshold for "moderate-to-high, non-crisis" — not tied to an actual
  `sessions` schema field/enum in this session. This is a hard blocker for `/plan-eng-review`,
  not a tuning detail** — the eligibility query cannot be written until this is defined
  against real schema values.
- **Resolved default (until `/plan-eng-review` revises it):** if all ambassadors are
  `active: false` at once, the eligibility query returns no match and the suggestion card
  silently does not render that session — no "no one's available" state in v1. This matches
  the rest of the pilot's minimal-surface posture (no new empty-state UI for a 6-person
  roster edge case); revisit only if this actually happens during the pilot.
- Copy for the suggestion card and the mandatory disclaimer — must avoid clinical framing;
  not drafted here.
- **Resolved by `/plan-ceo-review` (see `ceo-plans/2026-07-18-listener-suggestion.md`):**
  rate-limiting is IN SCOPE — a user-side cooldown field gates repeat suggestions within N
  days (exact N still TBD), plus a separate permanent per-user opt-out ("don't suggest this
  to me again") and PostHog analytics (shown/tapped/feedback) were added to v1 scope. An
  ambassador self-service pause toggle was considered and deferred to `TODOS.md`.
- What happens if an ambassador wants to pause/go inactive mid-pilot — the `active` flag
  handles removal from rotation, but not communicated process for how an ambassador signals
  this.
- **Longer-term, once the social layer ships in-app chat: will listeners be actual Xolace
  accounts (not just a hand-seeded roster), and could matching incorporate listener
  specialties/interests via RAG (e.g. matching a user's session content to a listener who has
  expressed interest in that kind of topic)?** Raised by the founder during this session as a
  forward-looking question, not in scope for v1 — the `ambassadors` table's flat shape in
  Approach A deliberately does not preclude this; a `specialties`/`interests` field could be
  added later without restructuring the eligibility query. Flagged here so it isn't lost, not
  decided.

## Success Criteria

- Suggestion-to-contact rate (of users shown the card, how many use the deep link) — the
  first-order signal of whether the nudge itself is wanted.
- Ambassador-reported qualitative signal (did the conversations that happened feel useful,
  safe, sustainable for them) — gathered via the same relationship the founder already has
  with the 6 ambassadors, not a formal survey system in v1.
- Zero "that felt wrong / unsafe" reports via the feedback link — the qualitative bar
  Premise #2's human-vetting tradeoff is meant to protect, given there's no platform-level
  safety net in v1.

## Dependencies

- Reuses `sessions` (intensity/emotion classification) and `escalation_events` (existence
  check only, per Constraints — no schema change needed to either).
- Reuses the existing feedback-tray system (`src/features/feedback-tray/`,
  `convex/productFeedback.submit`) for the "tell us" link — extends the `kind` union with
  `"listener"`, no new feedback schema, inherits existing rate-limiting and error handling.
- New `@vllnt/convex-flags` component dependency (global kill-switch + per-ambassador
  active/inactive override — see `/plan-ceo-review` Section 1).
- New `ambassadors` table and new `listenerSuggestions` table — schema additions required.
- Related but explicitly independent: Trusted Contact Notify (APPROVED,
  `nathan-chore-channels-research-design-20260718-082326.md`) and WhatsApp Follow-Up Delivery
  (APPROVED, `nathan-chore-channels-research-design-20260718-134117.md`), both on this same
  branch. This design does not supersede or depend on either — three separate channel/human-
  connection bets running in parallel on the same branch.
- Blocking, non-technical dependency: the ambassador-consent conversation (Premise #4) must
  happen before real-user launch, though it does not block writing the code.

## Deploy-Order Requirement

The `@vllnt/convex-flags` global kill-switch **must default to OFF at deploy time**, flipped
ON only after the Premise #4 ambassador-consent conversation completes for all 6 ambassadors.
Code can ship dark; the flag flip is the actual launch event. This prevents the exact failure
mode the consent gate exists to avoid — code shipping with the flag left in whatever state
a developer's local testing left it, exposing real users to the feature before ambassadors
agreed to its terms.
