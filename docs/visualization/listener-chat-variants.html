Listener Chat — three alternative UIs

Companion to research/listeners-chat-v2.md. The existing mockup (docs/visualization/listener-chat-mockups.html) is Variant A: Directory — browse a list of people, tap one, chat. These three change the information architecture, not the styling: what the unit of the feature is, where a conversation starts, and how much the UI promises about presence and response time. Same tokens from src/global.css, same existing components (BridgeCard, native tab bar, HeroUI Native primitives). Each variant carries the states the design review added to v1 — empty, pending, safety link — so they compare on equal footing.

Variant B
One door — no browsing, the app assigns
There is no directory. The tab is a single invitation: "Ask for a listener." Rotation logic already picks who is eligible on the backend, so the UI stops asking a person in a heavy emotional state to comparison-shop six strangers by bio. A face pile shows people exist without turning them into products. The choice-free path removes the worst failure mode of Variant A — a user scrolls three cards, can't pick, and leaves.
Unit One request. The person is a result, not an input.
Entry Session-end card and the tab both land on the same one-button screen.
Backend fit Uses the rotation/cooldown/volume-cap logic as designed. No directory query, no by_complete_and_active listing UI.
Scale risk Breaks down at 40+ listeners, where people reasonably want to choose.

Variant C
Threads from the moment — the conversation belongs to a reflection
The unit isn't a person, it's the moment that made you reach out. The tab lists your conversations, each headed by the mirror line that started it. Inside the thread, that line is pinned at the top, so both sides share context and the user never has to re-explain themselves to a stranger. This is the only variant that connects listener chat back to the core loop instead of bolting a messaging app onto the side of it.
Unit A conversation anchored to one session.
Entry Session-end card only — you can't cold-start a chat with no context. Browsing lives one level down.
Privacy cost Real. Sharing the mirror line with a listener needs its own explicit consent step, and the user must be able to send without it.
Backend fit Wants a sessionId on the chat request record; the eng plan doesn't have one yet.

Variant D
Letters — asynchronous by design, not a messenger
No bubbles, no presence dots, no typing indicators, no read receipts — and that's the product, not a v1 shortcut. You write something and it gets sent; a reply arrives later. Long-form serif type invites a paragraph instead of a one-word volley. This is the only variant where the UI's promise matches what six volunteer ambassadors can actually deliver, and it's the one most consistent with an app whose thesis is "not a chatbot, no back-and-forth."
Unit A letter. Turn-based, not real-time.
Expectation setting Built into the chrome — "usually replies within a day" is stated where a messenger would put "online."
Ambassador load Lowest. No implied obligation to be responsive; batch replies once a day is a legitimate way to use it.
Cost Least familiar pattern; a user who wants a quick back-and-forth will find it slow, and Stream's prebuilt message-list UI mostly gets discarded.

Comparing the four

The real split is what the UI promises. Variant A (the existing directory) and Variant B both promise a person; A promises a chosen person, B promises a person. Variant C promises continuity with your own reflection. Variant D promises a reply, eventually, and nothing more. Every other difference falls out of that.

Where they diverge most

A vs B is a choice-architecture argument. A directory is correct when supply is large and varied enough that choosing adds value. With six ambassadors it mostly adds a decision to someone who just finished a heavy session and may already be depleted — and it makes the zero-active-listeners state (launch day's actual state) into a visibly empty storefront. B's single door has no empty storefront; it has a sentence. B also throws away the least backend work: rotation already picks the listener, so the directory query is the piece that exists only to serve the browsing UI.

C is the only one that is Xolace-shaped. The other three would look identical in any peer-support app. Anchoring a conversation to the mirror line that caused it is the one idea here that uses the fact that this app already knows what the user is feeling. It is also the only one with a new privacy surface: sharing an AI reflection with a human listener is a materially different consent than "let me message you," and it needs its own explicit step plus a send-without-context path. That cost is real but bounded, and the payoff is that a listener opens the thread already knowing why they're there.

D is the honest one. A bubble thread with a green dot tells the user a person is present. Six volunteers are not present. Every messenger affordance the UI ships is a small promise the ambassadors have to keep, and the failure mode — a user watching an unanswered message at 2am — lands on exactly the person this feature exists to protect. D removes those affordances on purpose. The price is that it's the least familiar pattern and it discards most of Stream's prebuilt UI, which was part of the argument for choosing Stream in the first place.

Depth (small surface hiding real complexity)

B is the deepest: one button hides rotation, cooldown, volume caps, eligibility and the accept handshake, and its screen count is roughly half of A's. D is next — three screens, no presence system, no read state, no typing state. C is the widest surface: it adds the pinned-context card, its consent step, and a session-linked data model on top of everything a normal thread needs. A sits in the middle but pays for its width in states nobody sees at this scale.

Recommendation

Ship B's entry with D's thread. They compose cleanly and each fixes the other's weak spot: B removes the choice burden and the empty-directory problem at the front, D removes the false-presence promise at the back, and together they are fewer screens than the current directory design. Keep the roster reachable as a read-only "who's listening" sheet from B's "How this works" — that satisfies the eng review's directory decision without making browsing the primary path, and it's the piece to promote to a real directory once there are enough listeners for choosing to mean something.

Take C's pinned-context card as a later addition to whatever thread ships, not as its own variant. It's the strongest single idea in this set, but it carries a consent design that shouldn't be bundled into the same release as a brand-new chat surface and a new data processor.

Decisions these variants would change in the plan doc. B and D both drop or demote the directory, which reverses eng-review Decision 2 — worth re-confirming before schema work, since by_complete_and_active exists to serve that listing. C needs a sessionId on the chat-request record and a consent step that isn't specced anywhere yet. D makes the request/accept flow (the provisional addition pending 5 of 6 ambassadors) nearly free, since a letter already has no expectation of an instant open.
